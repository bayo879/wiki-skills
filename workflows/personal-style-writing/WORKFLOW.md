# 个人风格写作

## 适用

用户要求“按我的风格写”“参考我以前的表达”“根据知识库写一份汇报”等任务。
以已生成的 wiki 为主要资料入口，不重新扫描原始文件，不把工作流说明当事实来源。
风格只决定怎么表达，不改变事实、数字、完成状态或证据强度。

## 边界

命令在实际知识库工作区根目录执行，使用技能脚本实际路径，不切换到技能安装目录。
遵守技能工作区边界，不将 check 或 init 作为前置步骤。query 可能自动补齐账本与配置；
空账本不代表已有资料，没有可用知识时说明资料缺口，不为写作主动执行
init、ingest、next、submit、sync 或修改知识页。

## 步骤

1. agent: **明确任务**：确定主题、读者、用途、篇幅、时间范围、作者身份和输出形式。 已说明的信息不要重复问；缺失信息影响事实选择或风格归属时才澄清。
2. tool: **检索风格依据**：先按下方“称呼解析与作者归属”解析用户称呼，再用已核实的全名、 职务称谓变体、文体、“风格规范”“写作样例”等分别 query，不只搜索用户输入的简称。 执行 `python3 <skill>/scripts/wiki.py query "<称呼或关键词>" --json`， 对命中执行 `python3 <skill>/scripts/wiki.py query --page <page-id> --json` 读取知识页。已确认且适用于本次文体的风格规范可直接使用。 从样稿提炼风格时，必须沿页面返回的 `data.sources[].raw` 路径使用文件读取工具读取原文，观察原作者的句式、措辞和段落节奏； 不能把知识页整理者的摘要表达当成作者风格。核对作者与用途，归属不明的样稿不当个人风格依据。 优先选取同一作者、相近用途的 2–3 篇代表性样稿；只有一篇时注明样本有限，不推广为稳定偏好。 原文缺失或解析丢失排版时，只归纳可观察的特征，不推测标题、段落或排版习惯。 按下方优先级形成风格卡；样例归纳只是候选规则，不称为已确认的长期风格。 无依据时说明，可提供中性风格草稿，或请用户另行补充并摄入样稿，不冒充了解其风格。
3. tool: **检索本次事实**：围绕主题、项目名、业务别名、成果、问题换 2–4 组关键词 query。 使用上述 query 命令分组检索，再以 query --page 读取页面正文；原文过长时按文件读取工具的行号/偏移续读。 query 返回的话题可作检索线索，关键事实仍回到页面与 raw 核验。
4. agent: **分开整理输入**：
   - 表达规则：语气、段落长度、结构、常用词、禁用套话、标题排版，以及风格来源。
   - 事实清单：事实、事件日期、适用范围、状态、页面 id、raw key、核验情况。
   风格样例中的旧项目、旧数字、旧成果不得混入本次事实清单。
5. tool: **核验依据**：关键数字、日期、责任主体、状态或冲突需通过文件读取工具读取 `data.sources[].raw`。 stale 页面核验后才能使用，无法核验则待确认或排除。页面与 raw 冲突以 raw 为准并说明； 多份 raw 口径冲突则并列待确认，不自行选定。
6. agent: **按风格起草**：先定结构再写正文。区分事实、推断、建议与计划，推断明确标注。 不为模仿风格而补造成绩、立场、承诺、数字或经历，不将团队成果无依据归为个人贡献。 迁移表达规律而非大段照搬样稿；需要直接引用时明确引用边界和出处。
7. verify: **复核交付**：先对照事实清单检查时间、完成状态、数字、主体及来源，再按风格卡检查 结构、语气、句式和适用文体。润色后复查事实未改变。交付正文，另附关键结论的来源映射 与待确认事项，避免把核验流水塞入正文。
8. human: **条件确认与反馈**：身份歧义、核心事实冲突或任务缺少关键范围时，在对应步骤暂停询问用户； 没有这些条件就跳过确认，不必等写完才提问。用户要求保存或长期保留规则时，确认位置与授权。 本次润色默认只修改本次稿件。只有用户明确同意，才按技能正常渠道 持久化风格规则；不得直接改知识页或数据库，不把一次修改自动升级为长期偏好。

9. tool: **条件保存**：仅用户明确要求保存且合规位置与覆盖授权已明确时，使用文件写入工具 保存稿件并报告路径；遵守技能草稿存放边界，不编辑观看区知识页或原文。默认跳过此步。

## 称呼解析与作者归属

用户可能用“唐总”“王经理”等简称，而 wiki 中使用全名或历史职务。
先解析人物，再找风格样稿；简称不是唯一身份标识，以下示例不是固定别名词典。

1. **寻找身份线索**：先 query 用户原称呼，结合用户已提供的单位、部门、业务范围检索。
   没命中时可用姓氏作宽检索，再读候选人物页或相关页面确定全名；姓氏命中仅作候选，
   不等于确认身份。不能凭“唐总”自行编出“唐某”，也不能用姓氏相同就合并人物。
2. **建立本次称呼映射**：从 wiki/raw 或用户确认中记录简称、全名、单位/部门、
   不同职务及其适用时间、来源、确认状态。有多位同姓领导或身份冲突时，先询问用户
   “这里的唐总是指哪位/哪个单位？”，不能用搜索排名代替身份确认。
   依据足够且候选唯一时继续，并简述本次采用的人物身份，不要求用户重复确认。
3. **扩展检索**：确认“唐总”指唐某后，先单独 query “唐某”避免职务词限制召回；
   再依据已发现的称谓分别检索“唐某总经理”“唐某副总经理”，以及有空格、职务在姓名前等
   实际变体，结合“讲话”“署名文章”等补查。不把所有变体拼成一条唯一查询。
   当前关键词检索不保证识别别名；扩展由工作流执行，不宣称引擎已实现人物别名索引。
4. **核对职务沿革**：总经理与副总经理可能是同一人的不同时期，但必须结合单位、日期和
   原文证据核实，不能仅凭姓名相同就确认晋升、任职先后或当前职务。
   同一人历史职务下的样稿可作候选，按本次文体和适用范围选取；不把旧职务、旧职责、
   旧立场带入新稿。当前署名或职务不明时先确认或省略，不擅自称其为现任总经理。
5. **区分作者与被报道者**：标题或正文出现“唐某总经理”不证明文章是唐某所写。
   read raw 核对署名、发言人说明、讲话全文边界及转载出处。
   明确归属于该人的署名文章或讲话原文才可作为其表达样本；新闻中“唐总指出”的
   记者转述不能代表全文风格。少量明确直接引语只作局部弱证据，不用其推断整篇结构。
   代拟稿或归属不明的材料标注性质，不声称是本人原创风格。

在风格卡的适用范围和来源说明中保留本次人物身份、称呼映射依据及历史职务限制。
映射仅用于本次检索，不自动持久化、不修改知识页。缺乏身份依据时按阻塞项处理。

## 风格规则优先级与风格卡

表达规则按以下顺序选用，任何风格规则都不能覆盖事实核验与工作区边界：

1. 用户本次明确的表达要求。
2. 用户已确认且适用于当前文体的风格规范。
3. 同一作者、相同或相近用途的原始样稿。
4. 其他适用样稿归纳出的候选风格。
5. 中性、清晰的默认写作风格。

不能将邮件、讲话稿、正式公文的特点机械混用。同级规则冲突且影响成稿时先澄清，
不简单以文件修改时间判断偏好新旧。不把本次要求自动升级为长期规则。

起草前形成简短风格卡，作为本次工作依据，不默认保存或完整展示：

| 维度 | 本次规则 | 依据 | 确定性 |
| --- | --- | --- | --- |
| 结构 | 如结论先行，再列依据与行动 | 用户本次要求或页面 id / raw key | 已确认 / 样稿归纳 / 待确认 |
| 语气 | 如平实、克制、不夸大 | 同上 | 同上 |
| 句式与段落 | 只记录原文可观察特征 | 同上 | 同上 |
| 用词与禁用表达 | 常用表达、避免的套话 | 同上 | 同上 |
| 标题与排版 | 原文格式丢失时注明无法判断 | 同上 | 同上 |
| 适用范围 | 作者、文体、读者与用途 | 同上 | 同上 |

表中示例不是用户的默认风格，不得未经依据直接采用。样稿归纳注明样本数量和局限。
用户认为“不像我”时，优先询问或定位具体维度，再调整相关规则及正文，不无差别重写。

## 缺口与冲突处理

- **阻塞项**：作者身份或写作用途不明且影响归属、核心事实相互矛盾、关键结论无法核实。
  先提出必要问题，或提供不包含争议结论的框架，不生成看似完整的确定性稿件。
- **非阻塞项**：次要细节缺失、少量数字待补、风格样本有限。可继续给出有限草稿，
  在对应位置保留明确占位或省略无依据细节，另列待确认项。
- 无个人风格依据通常不阻塞中性草稿，但必须说明未实现个人风格；用户明确要求精准模仿时，
  先请求风格依据，不静默替换交付目标。

## 检索命令示例

替换占位符，多组关键词分别查询，不把长需求整句当作唯一查询。

```bash
python3 <skill>/scripts/wiki.py query "<作者名>" --json
python3 <skill>/scripts/wiki.py query "<文体或写作样例关键词>" --json
python3 <skill>/scripts/wiki.py query "<项目名或主题关键词>" --json
python3 <skill>/scripts/wiki.py query --page <page-id> --json
```

页面正文在 `data.body`；原始文件 key 与路径在 `data.sources[]` 的 `key`、`raw`。
用宿主文件读取工具打开实际返回的 raw 路径（相对路径以知识库工作区为根），
不按 key 猜路径、不跨工作区读取；raw 为空或文件缺失时标缺口，不为补原文自动摄入。

关键词排序不是覆盖证明；无命中不等于不存在。连续一轮无新增有效事实或足以完成任务时
停止，关键材料仍缺失则列出缺口，不无休止检索。

## 输出约定

1. **正文草稿**：符合用途、篇幅和文体。
2. **来源说明**：按“关键结论/事项 → 页面 id → raw key → 核验情况”对应列示，
   而非仅附一串来源；风格来源单列，注明已确认规范或原始样稿归纳，不混作事实证据。
3. **待确认事项**：风格不足、资料缺失、冲突、未核验的时间或状态；区分阻塞与非阻塞项，
   无则写“无”。必要时简述本次采用的风格规则及局限，不必每次展示完整风格卡。

默认直接回复，不自动落盘或发送。用户要求保存时，按技能工作区边界确认保存位置和覆盖授权，
已明确的信息不重复询问；未经授权不写入文件。保存后报告路径。不把生成稿自动摄入为事实来源。
不输出凭据和不必要的个人联系方式。
“不自动回写”指不主动提交内容修订或改变知识事实，并非保证工具完全只读：
现有引擎查询可能触发维护或发布行为，不能承诺查询绝无文件变动。

## 完成标准

- 已用 query 与 query --page 检索和读取 wiki，没有绕过知识库重新扫描资料。
- 事实与风格输入分开，关键事实可追溯到页面 id 与 raw key。
- 未把 stale 页面、样例旧事实、计划或推断伪装成已确认事实。
- 风格依据不足时明确说明，没有擅自保存长期偏好。
- 从样稿归纳时已读取原始 raw 并确认作者与用途，没有模仿知识页摘要的整理风格。
- 已按优先级形成风格卡并完成风格检查，解析丢失的格式未被臆测。
- 阻塞性冲突已澄清或降级为无争议框架；关键结论有对应来源，未擅自改变事实归属。
- 草稿与来源、缺口分开交付，说明未主动执行摄入、内容修订提交或发送。
