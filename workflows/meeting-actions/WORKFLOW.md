# 会议行动清单

## 适用

用户手里有一份会议记录（纪要、决策记录、会议录音转写稿、现场笔记），要把它变成能派活的
行动清单：谁在什么期限前做什么，每条都能回到原文那句话说。

只想要会议要点摘要、写会议报道、或按记录起草一份成稿文件，不适用：摘要直接答，成稿用
`personal-style-writing`，要 PPT 用 `ppt_creator`。

## 前置检查

- **会议记录在哪，先问清再动**：会话里已经有文件路径或会议系统链接就直接用；没有就在第 3
  步判定零命中时问，不靠猜文件名找。
- **记录未入库也照做**：`query` 命中 0 时不要先跑 `ingest`。用户给的是一份还没入库的文件时，
  直接读那个文件，避免留下排队任务卡住后续 `next`（`E_TASK_UNSUBMITTED`）。
- **图片、扫描件、录音不适用**：本技能不覆盖 OCR 与语音转写。识别到这类输入就停下，请用户
  提供文字稿，不硬拆。

## 步骤

1. agent: **提取会议信息**：通读整段会话，按六项归拢，每项标**已明确**（引用户原话、
   文件路径或链接）、**可推断**（写推断依据）或**缺失**：会议名、日期、参会人与各自角色、
   议题、记录所在位置、用户对清单的要求（要几条、要不要按人分组、给谁看）。
   缺失项只影响检索词选取，不影响拆解，不要为此反复追问。

2. tool: **检索记录**：换 2–4 组词 `query`，从会议名、日期、议题与本工作流内置词
   （会议、纪要、行动项、待办、决议、下次会议）组合，用
   `python3 <skill>/scripts/wiki.py query "<词>" --json`。记下命中页数、页面 id、标题与
   `snippet`，把检索命令和结果写进 `<任务目录>/cache/检索结果.json`。

3. human: **判定交接**：按第 2 步的命中数分三种走法，不混用：
   - **命中 1 份**：`query --page <id> --json` 取 `data.sources[].raw`，按该路径读观看区副本，
     进入第 4 步。
   - **命中多份**：把「标题 + 日期 + 路径」列给用户选，说明各自的议题差异；用户选一份再往下，
     **不自动合并**多份纪要——合并会造出原文里没有的结论。
   - **命中 0 份**：先问一句「这份记录是否已经入库？文件在哪（路径或链接）」。用户给出路径就
     直接读，不走 `ingest`；用户说还没整理成文件，停在这里等材料，不凭会议名编内容。

4. tool: **读原文**：用宿主提供的文件读取能力打开记录，不拼文件名、不凭命中标题猜内容。
   长文按 `##` 标题与段落切块，记下每个切块的标题与起止行号；把切块索引写进
   `<任务目录>/cache/原文摘录.md`，正文只摘与行动项相关的句子，不整段转存。

5. agent: **拆行动项**：逐句扫「要做、负责、截止、下周、会后、跟进、决定」这类表述，每条落六项：
   事项（动词开头、一个动作一句话）、负责人、期限、依据（原文逐字引文 + 切块标题或行号）、
   状态（待办 / 进行中 / 已完成）、来源（记录文件名或页面 id）。
   **负责人或期限在原文里没有写**时填「待确认」，不填「大家」「尽快」这类原文没有的说法；
   同一条出现两个负责人就并列写，让用户裁决，不自己择一。

6. tool: **建任务目录并写清单**：任务名用 `YYYY-MM-DD-<会议名>`（同名会议同日再加时段），
   目录固定在观看区的
   `wiki/workflows/meeting-actions/<任务名>/`，先
   `mkdir -p wiki/workflows/meeting-actions/<任务名>/{cache,output}`，
   清单写到 `<任务目录>/output/行动清单.md`，按「输出约定」排版。
   观看区内部被 `ingest` 整目录跳过，产物放这里不会触发摄入；**不落根目录、不写 `workflows/` 下**。

7. verify: **回溯核对**：从清单里逐条把「依据」引文回原文里找（`grep -F` 或再读对应切块），
   找不到就改成能对上的引文或删掉这条。再核两处：`output/行动清单.md` 的条数不少于原文里
   明确吩咐的动作句数量；负责人与期限都空的行都标了「待确认」。不一致就退回第 5 步重拆。

8. human: **交付确认**：给出清单路径、命中的来源（页面 id 或文件路径）、总条数与「待确认」条数；
   问一句要不要按负责人分组或补登期限。用户要改的字段改完即交付，不追问其余未定项；
   用户说「先这样」就停。

## 判断点

- **零命中不等于没有这份记录**：`query` 在空库或未入库时同样返回 0 命中且退出码 0，未建库时
  还会顺手建出 `.wiki`。所以要按第 3 步问用户，不据 0 命中下「记录不存在」的结论。
- **命中多份且用户不选**：只列候选并说明各自覆盖的议题范围，停在候选，不替用户拍板。
- **记录里只有决议没有分工**：照原文拆成行动项，负责人写「待确认」；不要在清单里编派活建议。
- **同一件事在原文出现多次**：合并成一条，依据引文把几处都列上，状态取最后一次提及的。
- **任务目录和投放副本同层**：观看区把 `<root>/workflows/<id>/` 首次投放到
  `<view>/workflows/<id>/`，但目标目录存在就跳过（`skills/llm-wiki/scripts/view.py:254`）。
  第 6 步建任务目录前先看一眼 `<view>/workflows/meeting-actions/WORKFLOW.md` 在不在；不在就
  先跑一次会推送观看区的命令（`status --json` 即可），让副本落位，再建任务目录。
  反过来做，那份副本永远不会出现，任务目录还会被当成投放结果。
- **原文含保密要求**（内部、密级、不得外传）：清单头部照抄该要求，产物只留任务目录，
  不外发、不进 wiki 知识页。

## 输出约定

任务目录与文件：

```text
wiki/workflows/meeting-actions/<任务名>/
├── cache/
│   ├── 检索结果.json        第 2 步的命令与命中
│   └── 原文摘录.md          第 4 步的切块索引
└── output/
    └── 行动清单.md          最终交付
```

`output/行动清单.md` 结构：标题行写会议名与日期；「来源」一节写记录文件名或页面 id、命中
方式（页面 / 直接读文件）；「行动项」一节用一张表，列为 `#`、事项、负责人、期限、状态、
依据、备注；表后列「待确认」小节，按负责人缺失 / 期限缺失 / 分工冲突分组。

## 完成标准

- [ ] 会议信息来源写清：命中的页面 id 或直接读的文件路径，命中数可复现
- [ ] 每条行动项都有「依据」逐字引文，能在原文里找到
- [ ] 负责人在原文没写的行都标「待确认」，没有编造或改用模糊词
- [ ] 产物只在 `wiki/workflows/meeting-actions/<任务名>/` 内，根目录与 `workflows/` 下无新增
- [ ] 用户确认交付，或明确说「先这样」

## 不做

- 不跑 `ingest` 把未入库的会议记录排队，不替用户决定入库。
- 不自动合并多份纪要，不把摘要把原文结论扩写。
- 不臆造负责人、期限、优先级；原文没有的字段一律「待确认」。
- 不把清单写成会议纪要正文、议题回顾或讨论过程——只留要人去做的事和依据。
