# 工作流评审

## 适用

用户点名一个工作流（`<view>/workflows/<id>/` 目录、`workflow list` 里的 id、`workflow:` 前缀后的 id，
或直接贴出一份 `WORKFLOW.md`），要判断它够不够用、有哪些不足、怎么改。只审已有对象；
用户要新建工作流时用内置 `workflow-create`，不套评审流程。

## 前置检查

- 对象必须能定位：拿到 id 就先 `workflow list --json` 对照；拿到粘贴文本时记下来源，结论里
  说明“审的是这段文本，不是仓库里的版本”。
- 内置工作流不给根目录相对的 `path`，只给 `skill_path`（技能目录相对，如
  `workflows/<id>/WORKFLOW.md`）；内置流程自包含、`resources` 恒为空，不能把空列表当
  `references/` 缺失问题。
- 对象存在未提交修改时，结论注明“审的是当前工作区版本”，把改动状态当上下文，不当缺陷。

## 步骤

1. tool: **取结构数据**：`python3 <skill>/scripts/wiki.py workflow list --json`，按 id 找到对象，
   记下 `valid`、`error`、`hint`、`warnings`、`resources`、`tools`/`human_steps`/`agent_steps`/
   `verify_steps` 与 `path`（内置项是 `skill_path`）。`valid: false` 时先按 `error` 与 `hint` 给结构修复项，再用
   `workflow load` 尽力取正文，能判的条目继续判。
2. tool: **取正文与分类型步骤**：`python3 <skill>/scripts/wiki.py workflow load "<id>" --json`，
   用返回的 `content`、`meta`、`steps`、`resources`；内置流程的细节都在正文里，项目流程按
   `resources[].path` 读引用文件。不自己按目录名拼文件路径。
3. tool: **验证检索命中**：换 2–3 个用户真会说出、但工作流名字里没有的需求词，
   `python3 <skill>/scripts/wiki.py workflow search "<需求词>" --json`，核对对象是否出现、
   `applies` 是否有内容、`score` 是否足以进入前 5。`applies` 为空时按「评审维度」第 1 条定位。
4. agent: **逐条判定**：按下面「评审维度」的七条逐条给“过 / 不足 / 不适用”，每条不足写证据：
   `WORKFLOW.md:<行号>`、`workflow list`/`workflow search` 的具体字段或值。不写“建议优化”
   “可以更清晰”这类无法执行的评价。
5. verify: **复核结论**：每条不足都能指到证据；结构问题（`valid: false`、空 `description`、
   没有 `tool:` 步骤）与内容问题分开列；没有读到的内容不判，标“未覆盖，需更多上下文”。
6. agent: **给最小修改**：每条不足配一句可直接照做的改法——改标题、补命令、拆步骤、加
   `verify:`、写失败路径、指定产物目录——并说明改完哪个输出会变好（如“`workflow search`
   的 `applies` 不再为空”）。不要求重写整个工作流，除非结构本身不成立。
7. verify: **成形结论**：按「输出约定」排结论；没有不足就写“未发现”，不凑条目；严重程度按
   “会让工作流无法加载 / 会让 agent 执行错 / 只是表达问题”三档排序。
8. human: **条件确认改造**：用户只说“看看”时停在结论，不改文件；要按结论改时，先列出准备改的
   条目等确认，改完重跑第 1–3 步复核，确认 `valid` 与 `applies` 都成立。

## 判断点

- `valid: false` 的错误是结构性的（缺主文件、缺 `description`、没有 `tool:` 步骤、正文超
  200000 字符），先修结构再谈其他，不把表达问题排在前面。
- `applies` 为空：先看 `## 适用` 标题是否精确（引擎只认 `^##\s+适用\s*$`），再看正文有没有
  真写适用条件。
- 步骤计数异常：`tools` 为 0 会被判无效；`verify_steps` 为 0 不是错误，但默认流程该有核对步。
- 一个 `tool:` 步里出现二选一、多组命令或“视情况”分支：拆成两个步骤，或写进判断点。
- `resources` 里的文件缺失，或正文引用了不存在的路径：按引用断链处理，不管引擎是否报错。
- 跨工作流引用（正文里的 `workflow load "<id>"`）：逐个能加载才算通过；引用不存在的 id 要指出。
- 结论与用户已有判断冲突时给证据，不为了让用户满意而让步；无法判定的标“待确认”。

## 评审维度

七条维度都按“过 / 不足 / 不适用”给结论，按顺序判：结构 → 命中 → 步骤 → 人 → 核对 → 失败路径 →
边界 → 完成标准。

### 引擎已经判的（不用重复审）

- `WORKFLOW.md` 存在、`description` 非空、正文非空、正文不超过 200000 字符。
- 有 `## 步骤`，每一步带 `tool:`/`human:`/`agent:`/`verify:` 类型，至少一步 `tool:`
  （纯人工流程会被判无效，并提示改写成 `process` 页）。
- 缺步骤节、步骤节为空、整份没有类型、单步没类型、类型后没内容，0.5.0 只给 `warning`
  （`W_STEPS_MISSING`、`W_STEPS_EMPTY`、`W_STEPS_UNTYPED`、`W_STEP_UNTYPED`、
  `W_STEP_EMPTY`），0.6.0 起判为不合法。
- 字段与命令面的完整定义在 `docs/readme/workflows.md`，这里不复制。

### 1 命中靠得住

- 判据：`description` 是“从 X 到 Y”的完整句；`tags` 用用户真会说出、但工作流名里没有的词；
  `## 适用` 标题精确；检索候选里的 `applies` 非空。
- 查法：`workflow search "<需求词>" --json`，看对象是否出现、`applies` 是否为空；
  读文件确认标题是 `## 适用` 而不是“适用与边界”“适用范围”一类变体。
- 失败样例：标题写成 `## 适用与边界` 时引擎取不到文本，`applies` 为空，候选页只剩
  `description`，用户看不到什么时候该启动。

### 2 步骤能执行

- 判据：每个 `tool:` 步写完整命令（`python3 <skill>/scripts/wiki.py … --json`），参数可替换，
  一步一个动作。
- 查法：读 `steps[].text`，抽查命令能否在工作区根目录直接执行；同一个列表项里数一下有几件
  独立的事。
- 失败样例：写“检索知识库并整理材料”，执行者不知道跑哪条命令；一个列表项塞进 8 条规则，
  执行时必漏。

### 3 人的位置对

- 判据：`human:` 只在需要拍板、授权或身份确认时出现；能取默认值并标注“按默认处理”的
  问句不占 `human:`。
- 查法：看 `human_steps[]`，逐条问“用户不回答时流程能不能继续走默认值”。
- 失败样例：把“请确认输出格式”写成阻塞步骤，用户没答就停住，而它本可以给默认值。

### 4 有核对步

- 判据：`verify:` 步给可判条件（数字、日期、来源、字段齐全、计数归零），不是“检查是否合理”。
- 查法：`workflow list` 的 `verify_steps` 计数，再读对应步骤正文。
- 失败样例：`verify_steps` 为 0，流程没有收口；或 `verify:` 只写“确认无误”，无法判定真假。

### 5 失败路径写死

- 判据：0 命中、命令报错、依赖技能缺失、记录未入库，各写明停在哪、报什么、不做什么。
- 查法：在步骤与判断点里逐个搜这些场景，缺一个记一条不足。
- 失败样例：只写顺路径，0 命中时临场编材料或换说法照常出稿。

### 6 边界与副作用

- 判据：不越界 `ingest`/`next`/`submit`、不改知识页、不写观看区副本；产物放任务主题目录下
  的 `output/`；跨工作流引用能 `workflow load` 成功；`resources` 引用的文件存在。
- 查法：读正文的命令清单与“不做”；对每个引用的 id 跑 `workflow load "<id>" --json`；
  按 `resources[].path` 确认文件存在。
- 失败样例：产物直接写在工作区根目录（会被 `ingest` 当来源排队），或写进定义目录
  `<view>/workflows/<id>/` 与 `WORKFLOW.md`、`scripts/` 混放；产物应在
  `<view>/runs/workflows/<id>/<task>/`。

### 7 完成标准可勾

- 判据：完成标准每条对应可观察结果；有“不做”清单防扩张；判断点覆盖已知冲突。
- 查法：逐条问“这句话能不能一句话判定真假”。
- 失败样例：完成标准写“质量达标、内容完整”，无法判定；没有“不做”，执行时顺手越界。

### 前提要素（新建前要先过）

评审已有工作流时只用于判断“它当初该不该存在”；新建时它是硬门槛，细则见内置
`workflow-create`：

- 会重复发生，有稳定触发词，不是一次性任务。
- 至少一个可写死的 `tool:` 步骤；纯人工流程应写 `process` 页。
- 完成状态能用一句话判定真假。
- 失败路径现在就能说清。
- 与已有工作流不重叠（先 `workflow search` / `workflow list`）。
- 产物有合规落点（任务主题目录 + `output/`）。

## 输出约定

1. **结论**：一句话加一档：可用 / 可用但有不足 / 不可用（结构不成立）。
2. **逐条不足**：按严重程度排序，每条写成
   `维度：不足 —— 证据 —— 改法 —— 改完的可见变化`。维度名用上面的七条原名，便于对照。
3. **实测项**：附上实际跑过的命令与关键字段（`valid`、`warnings` 计数、`applies`、
   `verify_steps`），不只写“我看过了”。
4. **未覆盖**：需要更多上下文才能判的条目写清缺什么，不当作通过。

## 完成标准

- 七条维度都给了判定，没有漏项也不重复计数。
- 每条不足都有可定位证据与可执行的改法。
- 结构问题与内容问题分开；`valid: false` 的对象同时说明存量问题与仍可判的条目。
- 检索命中实测过，`applies` 是否为空有明确结论。
- 没把“未读到的内容”写成通过，也没把“未提交修改”当成缺陷。

## 不做

- 不修工作流文件，除非用户确认改造范围。
- 不新建工作流（用 `workflow-create`），不改引擎命令、不改 `SKILL.md` 路由表。
- 不把评审结论写进知识页或话题。
- 不凭印象给结论：没有证据的条目直接标“未覆盖”。
