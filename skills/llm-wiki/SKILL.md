# llm-wiki

## 这是什么

- 源文件只读。要留下来的结论写进 wiki 页面，页面先进候选区，再由 CLI 发布。
- 页面是给后来人读的结论，不是源文件的转述。一页讲清一件事。
- 引擎都在隐藏目录里：页面树、索引、账本、版本、锁。这些由 CLI 维护，不要手改。
- 对外只有五条命令：`doctor`、`ingest`、`submit`、`abort`、`query`。转换、开轮、登记、版本锚点、索引都在命令内部。

## 用与不用

| 情形 | 怎么做 |
|---|---|
| 从零搭 wiki，或大改结构 | 用本技能，走完整摄取 |
| 找方案、查上次的结论 | `query` 搜；不要为了查而写页 |
| 一次性代码问题 | 直接读代码，不要写进 wiki |
| 简单问答 | 直接答；确定要留结论再写页 |
| 源文件本身 | 只读；要改去改源 |
| 一段对话里有值得留的判断 | 用 `llm-wiki-session`，不要手抄进 wiki |

## 开工三问

1. 这是该留的结论，还是一次性问答？
2. 三个月后还会有人查它吗？
3. 源在哪？先 `doctor` 看变动，再 `ingest` 把源转成可读的 raw。

## 最小序列

1. `doctor`：体检十项，有 Fail 先修；顺便看这一轮有哪些源变了。
2. `ingest`：扫仓库、转换、登记、开一轮，返回候选页的落点 `write_to` 与 `types`。给位置参数只摄入点名的源。
3. 读 `.wiki/raw/` 与其标出的受影响页，按《写页》把候选写进 `write_to`（`.wiki/staging/<type>/<id>.md`）。
4. `submit`：把整份暂存区发布进页面树、重建索引、记版本。发布不需要人点头，三道刹车只扣住命中的候选。
5. `query` 复验新页搜得到。

不写页、只是丢掉这一轮，用 `abort`：它丢候选但把源记为已复核，下一轮不再报同一变动。

## 三个停点

- `submit` 返回退出码 3（全部候选被刹车扣下）：停下来，把被扣的页和原因交给用户；只有用户明说要越过时才加 `--confirm`。
- 内容判断拿不准：两个结论冲突、该不该合并、要不要删页。停下来问。
- `doctor` 有 Fail，或无人值守链路连续失败：先修；不要用 `--confirm` 绕过。

## 报错跟随

- `error.code` 是分类，`error.message` 是下一步。先照 message 做，不要自己发明修法。
- `error.detail` 给出具体位置或原因时，以 detail 为准。
- 退出码 1：跑完了，但内容有问题，按 findings 修。
- 退出码 2：没跑起来，按 message 修。仓库没初始化时 message 会让你跑 `doctor --fix`：建完照它末尾的两步走（写项目指令、把无人值守摄入排成定时任务，周期照它说的先问用户）；已有 `wiki.toml` 不要重跑覆盖。
- 退出码 3：全部候选被扣，找人。
- 退出码 4：被锁，等正在跑的进程结束。
- 命令不在 PATH 上：先找项目里的构建产物，不要绕开 CLI 直接改 `.wiki/`。

## 写页

- 一页一件事；单源短内容并进已有页；三个以上独立源才值得新建。
- 结论变了不要静默覆盖：先写「以前认为……现在……」，再写改判依据。
- 证据只写源和页面，不写过程。
- 正文要能独立读懂；字段照 `SCHEMA.md`，拿不准就让 `submit` 的报错点名。

## 汇报

- 先说结论，再说写到哪一页；不要贴 JSON，也不要罗列执行过的命令。
- 没发布就说没发布；被扣下的说原因。
- 用户没问就不说内部账本、版本号、哈希。

## 按需阅读

- content.md：建页判断、写页、改写已有页。
- ops.md：体检、判断层、冲突与回退、忽略列表。
