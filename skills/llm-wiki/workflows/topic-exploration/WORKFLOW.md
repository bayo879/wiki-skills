# 话题探索

## 适用

用户问“是什么 / 怎么做 / 有哪些 / 有什么区别 / 帮我梳理”等需要综合多处资料的问题。
单点查页面、查字段、确认某个已知事实，不用整套流程，直接 `query`。

## 步骤

1. agent: **定主题**：用一句话写出探索主题、要回答的问题、覆盖范围和不覆盖什么。主题或目标含糊
   且会影响方向时，先问用户，不自行扩大范围。
2. tool: **找现成能力**：先用主题词跑一次 `query`，只看返回的 `workflows` 候选（每条带
   `applies`）；候选不够时再显式 `workflow search "<关键词>"`。只有 `applies` 与当前问题相符
   才 `workflow load "<id>"` 并按工作流执行；不符合就忽略，不要让工作流替用户决定范围。
   工作流说明“怎么做”，不提供事实依据。
3. tool: **找已有探索**：同一次 `query` 返回的 `topics` 是已沉淀话题；相关的按返回项的 `path`
   直接打开文件读全文，接着它的结论和未决问题，不重复劳动。
4. tool: **查知识页**：换 2–4 组关键词（同义词、上下位词、业务别名）跑 `query`，读命中页面；
   页面 id 是后续引用的依据。
5. tool: **补原始依据**：页面证据不足，或数字、日期、文号、责任主体需要核对时，按
   `query --page` 返回的 `sources[].raw` 打开观看区 `raw/` 副本（没有页面引用时看任务包的
   `work.json`），读原文；路径由引擎给，不自己拼文件名。页面与 raw 冲突时以 raw 为准。
6. agent: **判断收敛**：连续一轮没有新页面、新事实，或已能回答主题问题，就停止检索。检索命中是
   排序子集，不是覆盖证明；没查到不等于不存在。
7. agent: **总结**：先结论，再依据（页面 id、话题名；源文件用 `query --page` 的 `sources[].raw`
   定位），再冲突、缺口和未覆盖范围。不把推断写成事实，推断标“据此推断”。
8. human: **问沉淀**：默认问用户是否把主题沉淀到 `<view>/topics/`。用户只要一个事实、没有可复用内容时，
   说明“这次没有需要沉淀的内容”即可，不硬造。
9. agent: **沉淀（用户同意后）**：按下面的“话题文件”写，并同时给出两项后续：
   - **能力候选**：流程稳定、可重复执行时，建议沉淀成 `<view>/workflows/<id>/WORKFLOW.md`；
     先给草稿，用户确认后再建，不直接改工作流。
   - **资料深挖**：列出待摄入的来源、待补的页面、下一轮要查的具体问题（带建议关键词）。
   - **依据落点**：把本次用到的页面、原文、话题、工作流按四类前缀写进「依据」，写完 `query`
     复核 `refs`/`missing`。

## 判断点

- 命中的工作流没有页面：按工作流办事，事实另找 raw 或页面；不把工作流当事实依据。
- 页面与 raw 冲突：以 raw 为准，在总结里说明冲突位置。
- 资料在工作区外：停下来让用户把目录作为工作区打开，不跨区读，不复制到区外。
- 主题过大：拆成 2–3 个可回答的子问题，先答最影响决策的那个；其余写进话题的“未决问题”。
- 已有同名话题：并入原文件，不新建重复话题；结论变化时写清改判依据。

## 话题文件

位置与命名：`<view>/topics/<主题>.md`，一个主题一份（目录名固定用英文 `topics/`，与
`<view>/workflows/` 对齐；旧根 `<root>/topics/` 只作只读兜底）。文件名用能检索的主题词，不用日期或
“会话记录”这类名字。

frontmatter 建议写，缺了也能被 `query` 检索：

```markdown
---
name: 主题名
description: 一句话说明这个话题回答什么
status: open
updated: 2026-01-01
---
```

`status` 取 `open`（还有未决问题）或 `done`（已收敛）。

正文固定六节，没有内容就写“无”：

```markdown
## 主题

要回答的问题、范围、不覆盖什么。

## 结论

先给结论，一段话能说清就不拆成条。

## 依据

- 页面：`<page-id>` — 支持了哪条结论
- 原文：`<观看区 raw 路径>` — 关键数字或日期的出处（取 `query --page` 的 `sources[].raw`，
  抄整条或只抄 `raw/` 之后的部分都行）
- 话题：`<话题名>` — 上一轮的结论与未决问题
- 工作流：`<id>` — 流程依据（不是事实依据）

## 未决问题

还需要确认什么，卡在哪里。

## 下一步

可执行的下一步：建议关键词、待摄入文件、待补页面。

## 能力候选

是否值得沉淀成工作流；值得就写工作流 id、触发条件、还缺哪几步。
```

写作要求：

- 写结论、理由、适用条件、未确认事项；不抄整段原文。
- 区分实测事实、用户约束与推断；候选方案标为未验证。
- 内容脱离聊天也能读懂；三个月后能据此接着做。
- 不写密码、Token、API Key、个人联系方式。

## 沉淀前的归属判断

- 项目事实（目录、命令、配置、已实现行为）：归项目产品文档，不写话题。
- 必须持续生效的规则：归对应层级的指导文档；规则变更要用户授权。
- 未决问题、待实现、待验收：归项目 issues，不包装成已有能力。
- 可复用的方法、经验、踩坑、方案取舍，以及一次探索的过程与结论：写话题。
- 临时命令、调试流水、没有复用价值的对话：不保存。

## 授权与安全

- 用户明确要求沉淀且主题清楚：直接写，不重复问同一授权。
- agent 主动提议：先给标题和一句话要点，征得同意再写。
- 范围含糊或含敏感内容：先澄清，必要时脱敏；凭据不落盘。
- 用户明确不留：不写。

## 完成标准

- 总结回答了主题问题，结论能回溯到页面 id（源文件用 `query --page` 的 `sources[].raw` 定位）；
- 冲突、缺口、未覆盖范围写清楚；
- 用户对是否沉淀有明确答复；写了话题时，文件符合上面的格式，并报告路径与“未执行摄入”。
- 依据里的引用 `query` 后 `missing` 为空，或已说明为什么留着坏链。
