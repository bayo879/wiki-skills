# 新建工作流

## 适用

用户要新建、起草或搭建一个可执行工作流（“建个工作流”“把这个流程写成工作流”“给 xx 造个
工作流”），或要把一段现成步骤固化成 `workflows/<id>/`。只产出工作流文件；改引擎、命令面或
技能自身的动作走技能维护，不在这里做。

## 前提要素

用户要建工作流，前提是它有可能通过评审。逐条确认，任一不成立就先停，给替代方案，不产出
无法优化的流程：

1. **会重复发生**：有稳定触发词，不是一次性任务；一次性的写进这次交付物或知识页。
2. **至少一个可写死的工具步骤**：引擎要求 ≥1 个 `tool:`；全靠人判断的写 `process` 页或话题。
3. **完成状态可判**：能用一句话判定做完（文件存在、字段齐全、计数归零）。
4. **失败路径可写**：0 命中、命令报错、依赖缺失时停在哪、报什么，现在就能说清。
5. **与已有工作流不重叠**：先 `workflow search` 与 `workflow list`；同名或近义已存在就扩展它。
6. **产物有合规落点**：按任务主题建目录，最终产出放该目录的 `output/`，不落工作区根目录。
7. **层级清楚**：改技能行为或命令面 → 技能维护；只是本项目做法 → 项目 `workflows/`；
   确实全场景通用且技能维护者认可 → 内置 `skills/llm-wiki/workflows/`（内置只读、随技能分发）。

## 前置检查

- 先确认触发词是用户真会说、且与已有工作流不冲突；已有同义流程时按第 5 条改为扩展。
- 内置工作流只读：改内置流程要复制到项目 `workflows/<id>/` 再改，不同步改技能安装目录。

## 步骤

1. tool: **查已有工作流**：`python3 <skill>/scripts/wiki.py workflow search "<需求核心词>" --json`
   与 `workflow list --json`；命中同 id 或同义流程就改为扩展，不新建。
2. agent: **前提校验**：按「前提要素」逐条给“过 / 不过”，每条带一句依据；不过的写明替代方案
   （`process` 页、一次性交付物、扩展现有工作流）。
3. human: **条件确认**：任一前提不过时，先给替代方案并等用户确认；用户确认仍要建时，把缺口
   写进 `## 边界` 或「不做」，不假装已满足。前提全过时给出目录名、层级与产出位置。
4. agent: **定 id 与层级**：id 用英文；项目版写 `workflows/<id>/`，内置版写
   `skills/llm-wiki/workflows/<id>/` 并由技能维护者提交。
5. agent: **起草 WORKFLOW.md**：frontmatter 写 `name`（英文机器名）、`description`（一句
   “从什么到什么”的完整句）、`alias_name`（中文展示名）、`tags`（用户会说出但名字里没有的词）；
   正文含 `## 适用`（标题必须精确，写触发词与不适用场景）、`## 前置检查`、`## 步骤`、
   `## 判断点`、`## 输出约定`、`## 完成标准`、`## 不做`。
6. agent: **写步骤**：按 `tool:`/`human:`/`agent:`/`verify:` 标类型，至少一个 `tool:` 写完整
   命令；一个步骤只做一件事，分支写进判断点。
7. agent: **写 references**：只有执行时才需要读的细节（字段表、模板、错误码）放
   `references/`，正文只留一句引用；内置流程自包含，细节直接内联。
8. tool: **机器校验**：`workflow list --json` 确认 `valid: true`、`error` 为空、四类步骤计数与
   预期一致；`workflow search "<触发词>" --json` 确认能命中且 `applies` 非空。
9. verify: **按评审标准自审**：用内置 `workflow-review` 的七条维度逐条判，结构问题先修；
   每条不足给证据与改法，改完重跑第 8 步。
10. human: **条件提交**：列出准备提交的文件与新增的目录约定等用户确认；改内置要说明影响所有
    安装该技能的项目。

## 判断点

- 前提不过又坚持要建：把缺口写进 `## 边界` 或「不做」，不写假的步骤凑数。
- 已有同义工作流：扩展它，不新建；确实要并存时在两边 `## 适用` 写清区别。
- 步骤里出现二选一或“视情况”分支：拆成两步，或写进判断点。
- 产物要写进工作区根目录或观看区投放目录：改为任务主题目录 + `output/`。
- `workflow list` 报 `valid: false`：按 `error` 修到通过，再走第 9 步。
- 触发词与已有工作流冲突：改 `description`/`tags` 或合并，不靠重叠标签抢命中。

## 输出约定

- 前提校验结果（逐条过/不过 + 替代方案）、目录与 id、`WORKFLOW.md` 正文、`references` 清单、
  机器校验摘要、自审结论。
- 前提未全过时先给替代方案与缺口，不直接产出工作流文件。

## 完成标准

- 7 项前提都有明确结论；未过项有替代方案或明确的边界记录。
- `workflow list --json` 显示新增工作流且 `valid: true`、`error` 为空。
- `workflow search "<触发词>" --json` 命中该工作流且 `applies` 非空。
- 至少一个 `tool:` 步骤含可执行命令；有 `verify:` 核对步；有失败路径与可判的完成标准。

## 不做

- 不改引擎、命令面、`SKILL.md` 路由或 `health.py` 的内置清单——那是技能维护。
- 不为一次性任务建工作流；不把纯人工流程写成可执行工作流（应写 `process` 页）。
- 不在前提未满足时假装满足并伪造步骤。
- 不把工作流写进知识页、话题或观看区投放目录。
