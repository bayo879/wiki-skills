# 恢复手册：命令跑不动时看这里

命令失败时返回的错误对象里，除了 `code`、`message`、`next`，还有两项：

- `doc`：本文件的绝对路径；
- `section`：本文件里对应的小节标题。

先按 `error.next` 处理；`next` 说得不够，就翻到 `section` 指定的那一节。只有这两项都没给
的错误（载荷校验、任务并发这类），按 `SKILL.md`「提交失败」处理，不在这里。

两条通用前提：

- **不要手改 `.wiki/` 下的数据库、任务文件和锁**，也不要靠删锁抢跑。本文件给的做法都是
  命令或整目录操作。
- 要删 `.wiki/` 之前先备份（`cp -r .wiki .wiki.bak` 或整目录复制到工作区外）。账本里没有
  从观看区反向重建页面索引的路径，删了就得重新摄入、重新写页面。

## 怎么读一个失败

```bash
python3 <skill>/scripts/wiki.py ingest --json   # 失败时 stdout 仍是一段 JSON
```

退出码含义：`0` 成功（含“没有变化”“任务被跳过”），`1` 命令失败，`2` 用法或载荷不合法，
`3` 状态冲突（账本、任务、来源），`4` 工作区被占用。

自动补齐只有一种：任何打开账本的命令（`init`、`ingest`、`next`、`submit`、`query`、
`status`、`doctor` 等）在打开时，缺的目录、缺的 `wiki.json`、缺的表会当场建出来，
补了什么写在返回值的 `repaired` 里（路径列表，和 `created` 同形）。`repaired` 非空不是错误；
它说明这条命令顺手把库补全了。`check`、`workflow`、`version` 不碰账本，也不会建库。

## 运行时与安装

对应 `E_HEALTH`。`check` 的安装级检查覆盖解释器版本、技能文件是否齐全、工作区是否可写；
这条错误说明其中一项不满足，命令没有开始处理账本。

- 解释器低于 3.12：换一个 3.12 或更高的解释器跑命令。Windows 上运行
  `scripts\bootstrap.ps1` 让它找已有的 3.12+（agent 自带运行时用 `-Python <python.exe>`
  指定）；它不下载也不安装 Python，找不到时同样报 `E_PYTHON`。
- 提示技能文件缺失：技能目录被部分复制或删除过，重新安装整个技能目录，不要只补单个文件。
- 提示工作区不可写：换到工作区里一个可写目录再跑，或修权限；不要把 `--root` 指到工作区外。

不要为了让检查通过去改技能目录里的文件、改 `wiki.json` 里的路径，或跳过命令直接改账本。
检查失败时它本来就没写任何东西，修好环境重跑即可。

## 工作区不可写

对应 `E_HEALTH`，失败项是 `workspace`，`detail` 形如 `not writable: …`。

说明当前目录不能被写入（只读挂载、移动硬盘、已被清理的临时目录，或权限被改过）。换到
工作区里一个可写目录再跑，或请用户修权限。不要用 `--root` 指向工作区外来绕，那只会换成
`E_PATH`。检查失败时命令没有写入任何东西，修好重跑即可。

## 旧账本

对应 `E_STATE`，`message` 形如 `ledger schema is older than this skill: sources, raws`。

这个技能**不做迁移**：旧版本写的账本里已有数据时，直接拒绝继续，避免把旧结构当新结构写坏。

处理：

1. 备份：`cp -r .wiki .wiki.bak`（页面内容在观看区 `wiki/pages/`，账本外的副本也留一份）。
2. 删掉账本：`rm -rf .wiki`。
3. 重新建库：在工作区跑 `ingest`；重新摄入来源、重新排任务、按任务重写页面。

旧账本里的页面不会自动回来：观看区的页面文件只是账本的输出，没有反向导入索引的命令。
页面内容还有价值时，先手工把 `.md` 拷到工作区外留档，重建后按新来源重新写。

例外：旧结构的表**全是空表**时不需要人工介入，引擎会直接按当前结构重建这几张表，不算
迁移。所以真正的空库不会走到这条错误。

另一种 `E_STATE` 不是账本问题：`message` 说某页面已有未关闭的任务、或任务已被领取，属于
并发冲突，重新 `next` 拿当前任务再提交，不要去删 `.wiki/`。

## 配置损坏

对应 `E_CONFIG`，`message` 形如 `cannot read .wiki/wiki.json: …` 或 `publish.dir … 不合法`。

`.wiki/wiki.json` 只有一段配置：`publish`（观看区目录名、是否发布页面、话题和场景）。两种
修法：

- 手工改回合法 JSON：注意它是 UTF-8、不带 BOM，`publish.dir` 只能是一个目录名（不能是
  绝对路径、`..` 或空字符串）。
- 直接删掉 `.wiki/wiki.json`，下一条命令按默认值重建（默认 `dir` 为 `wiki`，三项发布开关
  都为 `true`）。

删文件前先看一眼里面有没有自定义过的 `publish.dir`：换过观看区目录名的话，重建后默认值会
指回 `wiki/`，旧观看区里的手改内容不会自动跟过来。

## 账本损坏

对应 `E_DB`，`message` 形如 `ledger cannot be opened: file is not a database`，或
`.wiki/wiki.db` 通不过完整性检查。

这类错误说明账本文件本身坏了（磁盘错误、被别的程序写过、复制时截断），引擎不会尝试修复：

1. 停手，不要再往这个工作区写。
2. 有备份就从备份整目录恢复 `.wiki/`（只恢复 `wiki.db` 也行，但要和 `wiki.json` 一起）。
3. 没有备份就按「旧账本」的步骤：备份后删 `.wiki/`，重新 `ingest` 重建。

不要用 sqlite 工具手工改表、也不要只删 `wiki.db` 了事（`wiki.json` 里的配置和观看区状态
会和新建的库对不上）。

## 工作区边界

对应 `E_PATH`，`message` 形如 `wiki root … is outside the workspace …`、`ref escapes the
workspace root`、`publish dir … resolves outside the workspace root`。

- 命令跑在了工作区外：`cd` 回工作区根目录再执行。`--root` 只接受当前目录或它下面的子目录。
- 观看区是符号链接、指向工作区外：把 `publish.dir` 改回工作区内的真实目录，或删掉这个链接。
- `query` 的词或 `--payload` 用了 `../` 跳出工作区：换成工作区内的路径。

边界是有意划的：跨区扫描、读写、软链把数据搬出去，都不会被放行，改路径比绕边界省事。

## 工作区被占用

对应 `E_BUSY`：另一个 wiki 进程正在这个工作区写账本。等它结束再重试；只有确认它已经崩溃
（进程不存在、`.wiki/lock` 超过十分钟没动）才删 `.wiki/lock`，不要为了抢跑直接删锁。
