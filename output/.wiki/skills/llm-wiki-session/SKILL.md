# llm-wiki-session

## 这是什么

把一段对话里值得留下的东西，写成 wiki 页面。产物是**页面**，不是聊天记录：原始会话不存，只留结论、理由和坑。

页面写进 `[ingest].session_dir`（默认 `sessions`）指向的源目录，走和别的材料一样的路：`ingest` 登记、agent 逐任务提交载荷、根收尾合并并确认来源。落在这个目录下的页面照常入库、默认也在检索结果里，`query --no-archive` 才按这个目录前缀排除它们——它们是背景，不是日常答案。

## 什么时候用

- 一段会话里出现了「当时为什么这么定」的判断，而项目文档里只有结论。
- 用户说「记一下」「留给下次」，且内容是通用经验或跨会话的决策依据。
- 同一件事之前已经有过一轮讨论，这次是补充或推翻。

以下不用：

- 项目事实（目录结构、命令、配置）——写项目 README 或 AGENTS，不写 wiki。
- 一次性调试过程、临时命令、没结论的探索。
- 用户明确说不留。

## 抽什么

一条会话通常只值得留两三件事。按这个优先级挑：

| 值得留 | 不值得留 |
|---|---|
| 决定与它的理由（「选了 A 不选 B，因为 C」） | 试过哪些命令、报了什么错 |
| 发现的反直觉事实（「X 看起来该这样，实际不是，原因 Y」） | 代码里能直接读到的结构 |
| 踩过的坑与它的触发条件 | 一次性的环境问题 |
| 用户定下的约束（「必须支持 Node 22」） | 会议过程、来回推敲 |

判断标准：三个月后的 agent 读这一页，能不能更快做对同一件事？不能，就别写。

## 怎么写

- 一页一个主题，不按时间切；同一件事的后续讨论并进同一页。
- 开头的摘要写「这条会话留下了什么判断」，不写「本次讨论了……」。
- 决策页写：当时的问题、可选项、选了什么、为什么、后来是否被推翻。
- 被推翻的结论保留原文并标注「现已改为……」，不要删。
- 正文不写「用户说」「我说」，写成事实与理由。
- 链接用 `[[页面 id]]`；`sources` 与 `updated` 由工具填写，不用手写。

## 流程

先确认目标工作区根，使用该根 `.wiki/cli/llm-wiki` 的绝对路径（Windows 为 `llm-wiki.exe`），不使用 PATH 旧版；根不明确就问用户，不能从已复制的技能目录或当前目录猜测。下面的命令与 `[ingest].session_dir` 都以该工作区根为准；写素材时也使用该根下的绝对路径。首次接入请阅读目标根 `.wiki/readme.md`。

1. 先 `query` 搜同主题，有页就并进那页，不新建。
2. 把页面落到 `[ingest].session_dir` 下的路径（例如 `sessions/2026-10-29-cli-reshape.md`）。
3. `ingest` 登记这份材料并保存 raw 哈希；按交付的任务视图提交载荷：route 交信息点与归属，page 交标题、摘要、标签、状态与完整正文；frontmatter、sources、updated 由工具渲染。
4. 按返回的 `outcome` 与 `remaining` 推进；根收尾核对四道哈希，漂移则重读、重试，不会撤销已合并的页。
5. 向用户报一句话：留下了哪些判断，写在哪一页，是否仍有未确认来源。

## 边界

- 不存原始对话：没有摘要价值的过程不落盘。
- 不写项目文档里已经写清的事实；重复等于制造两个真相源。
- 写入前先给用户看标题和一句话要点，得到明确同意再写。提交后没有发布门，根收尾即合并生效。
- 没有自动备份与工具内回退；并发作者可能覆盖同一页，写前重读并确定唯一作者。
