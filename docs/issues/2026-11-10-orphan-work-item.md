# 源被删除或改成配不上的内容后，来源待办清不掉

登记：2026-11-10　状态：未完成　优先级：P2

## 问题

`done <KEY> --hash <RAW_HASH>` 在清待办前会 `read_source(源)`（`src/worklist.rs:116`）。
源文件已被删除时返回 `HashError::Io` → `E_IO` exit 1，不是漂移，也不是「无动作」；
源被改成无法与账本配对的新内容时同样报漂移并保留待办。

现在没有任何收口路径：

- `ignore --add` 只写 `.wiki/ignore`，不清 `work_items`；
- `sync` 对缺失源只把相关页标 stale（`src/sync.rs:257` 起），不动待办；
- `done` 没有 `--force` / `--forget`。

## 影响

作者删掉一份不想再要的资料后，那条待办每轮 `ingest` 都会继续交付，agent 反复看到
一条永远无法完成的来源；只有直接改数据库才能清掉。

## 候选方案（未定案）

1. 源不存在时 `done` 视为「来源已消失」，直接清待办并说明原因（需要显式
   `--force` 之类开关，避免误清）。
2. 新增 `done --forget`：不核对源与 raw，只清指定来源的待办；审计留给输出，不写日志。
3. `ignore --add <KEY>` 顺带清掉该来源的待办（把「永久不看」与「待办」绑定）。

都不解决「源改名且新键无法配对」的情形——那种情况要等 `moves` 或人工处理。

## 待确认

- 「来源消失」是否等于「这条资料已被抛弃」，还是可能只是临时移走。
- 清待办是否必须留下人类可见的记录（现在没有 journal）。

## 验收条件

- [ ] 三种情形（删除、改成无法配对的内容、改名成功）各有一条测试，结局明确且不误清其他来源。
- [ ] 重复确认的幂等前提写进文档：raw 与源都还在时才返回 exit 0 无动作。
