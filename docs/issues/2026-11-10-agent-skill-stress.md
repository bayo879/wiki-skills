# 多 agent 压力场景下的技能纪律验证

登记：2026-11-10　状态：未完成

## 问题

技能（`skills/llm-wiki/` 三份与 `skills/llm-wiki-session/`）现在只被机器守了「静态形状」：

- `tests/skills_pack.rs`：只发两个技能、frontmatter 两项、正文行数上限、引用的子命令真实存在。
- `tests/docs_contract.rs`：技能不写 JSON 字段路径、闭世界词表、`E_*` 存在。

这些保证「没写错名字」，不保证「agent 按门禁顺序做事」。历史上的 A/B 实测只覆盖四个
单任务（读技能 vs 裸跑 CLI），没有覆盖：多 agent 并行写页、长会话中途被打断后恢复、
同一来源被两个 agent 同时认领、只读了一半 raw 就调 `done`。

## 影响

- 技能里最关键的是顺序与门禁（`ingest` 给 `write_to` 与 raw 哈希 → 读 raw → 写页 →
  `done` 只认实际读过的哈希）。顺序错了，机器不会红，只会得到错误的完成状态。
- 并发两个 agent 写同一页会互相覆盖，CLI 锁只约束工具命令，不约束手工写文件；这条
  风险已写进文档，但没有场景化验证「文档提醒是否足以让人避开」。

## 候选方案（未定案）

- 用固定脚本回放几个压力场景（并发认领、读到一半被打断、旧哈希重试），记录 agent
  实际动作序列，与技能要求的顺序对比；只做评估，不把结果写成产品契约。
- 评估指标用「是否出现误清待办 / 静默覆盖 / 用新哈希为旧阅读背书」这类可判定的错误，
  不用主观评分。

## 待确认

- 评估在哪个 harness 上跑、要不要保留可重放的提示词与初始仓库快照。
- 结果只作为技能改写的依据，还是也进常规回归（后者成本明显更高）。

## 验收条件

- [ ] 至少三个场景有可重放的脚本与初始仓库快照。
- [ ] 结论能回答「技能是否真的改变了 agent 的行为」，而不是「agent 能否完成任务」。
