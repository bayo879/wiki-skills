### 已确认的实现缺陷与待验证机制

- `src/parse/pdf.rs:82-101`：探测返回 false 就直接生成附件链接，跳过正文提取。
- `src/parse/pdf.rs:118-133`：直接 `Document::load_mem(bytes)` 后读取页面内容，探测前没有显式检查加密状态或解密；`get_page_content` 的 `Err(_) => false` 把读取失败折叠成“没有文字”。加载失败反而返回 true，错误语义不一致。
- 依赖 `lopdf 0.32.0` 的 `Document::get_page_content` 还有下层降级：取流对象失败时跳过；解压失败时返回原始流字节。故不能仅把上层 `Err(_) => false` 改为报错就宣称修好本批样本；需要验证探测是否实际扫描了加密/未解压字节。本次未运行 Rust 层逐页探针，RC4 的具体影响仍待复现确认。
- `src/parse/pdf.rs:136-163`：只抽查头、中、尾最多六页，没有抽查到文字不能证明整份文件没有文字。还应覆盖文字只出现在未抽样页、通过 Form XObject 绘制文字等情况；这些属于代码审查风险，尚无本批样本验证。
- `src/convert.rs:358-378`：raw 持久化正文、解析器及两个标记，但不持久化本次解析 warnings。`src/parse/mod.rs:328-341` 对 asset 直接豁免低字符数告警。使用者只读 raw 时容易把占位当作转换后的内容。
- `src/parse/mod.rs:390-415`：配置外部后端时低质量/附件结果会尝试外部，但外部失败仍返回原有结果并附告警；这不代表正文已恢复。未检查用户配置或调用其外部服务，不将外部可用性写成已验证事实。

### 其他格式的同类风险（静态审查，不冒充实测缺陷）

本轮审查了文本、HTML、图片后端及公共回退逻辑；未找到该来源目录的 DOCX 样本，未运行全格式样本集。

- 文本：`src/parse/text.rs:43-73` 对非 UTF-8 输入替换坏字节并返回成功、对空正文仅告警；`src/parse/mod.rs:281-289` 的 auto 不对文本尝试外部。GBK 等编码可能成为乱码而非显式失败，需要针对样本验证。保留原始字节与“内容可靠可用”是两回事。
- HTML：`src/parse/html.rs:53-83` 同样以 UTF-8 有损解码并仅告警；`src/parse/html.rs:99-111` 只取首个 article/main/body；`src/parse/html.rs:152-184` 没有表格结构专门处理。可能出现正文遗漏、表格关系丢失，但字符数仍超过阈值，auto 不会因语义丢失而回退。需用多 article、GBK、表格与脚本渲染页面验证，不在本 issue 中宣称所有 HTML 已损坏。
- 图片：`src/parse/asset.rs:50-70` 本来就只产生链接，不读取图片文字；`src/parse/mod.rs:276-300` 图片即使配置外部也走内置。属于当前能力边界，不是已实现 OCR 的故障，但不能将其表达为图片正文已摄入。
- DOCX/XLSX/PPTX：当前注册后端不认领这些格式，见 `src/parse/mod.rs:233-263`。不应宣传为支持；后续检查扫描入口是否显式提示跳过，而不是误以为已处理。此次未验证扫描端行为。

## 影响

这不是一份扫描件的偶发现象：本次检查的六份 PDF 全部没有进入可供知识整理的正文形态。若仅凭 raw 存在或“转换成功”推进，后续检索、总结与知识页整理会缺少真实材料，并可能误将解析器失败解释为原件没有文字。缺少持久化质量信息也影响后续排查和重转判断。

本次没有验证下游是否已经将这些来源结算，不宣称已经发生知识页污染或来源丢失。禁止直接删除 raw、重置账本或覆盖用户手工内容来掩盖问题。

## 候选方案

已确认需求：修复有文字 PDF 被误判并保存为占位的问题，并检查其他文件的同类内容丢失风险。

2026-11-12 spec 讨论已确认的方向（尚未实现、尚未验收）：

- 采用方案 A：修复现有 Rust 解析链路，允许根据实际根因评估依赖升级；本轮不引入 `pdftotext` 本地备用依赖。
- 本轮不新增 OCR。扫描件和图片若现有能力不能取得正文，归入未处理/失败清单，沿用现有流程在最后收尾统一汇报，不阻断其他文档。
- 不能仅因生成了附件链接就当作正文转换成功；不能将解析失败断言为原件没有文字层。需要保留文件名和失败原因供收尾汇总。
- 已知有页面读取或提取失败，即使其他页面已有正文，整份文档仍按转换失败处理；不把这份残缺结果作为正常来源交给后续整理。此规则不等同于保证逐字正确，具体可检测范围须在 spec 中明确。
- 存量错误占位采用显式触发的受保护重转：升级不自动批量重写，由用户主动发起；源内容未变化也能触发。“一次”不表示只能使用一次。保护 pin 与手工修改，重转失败保留旧结果，成功后重新进入正常整理流程。具体命令与保护机制尚待设计。

以下具体设计仍待 spec 确认：

1. 将探测结果区分为“发现文字 / 确认没有文字 / 无法判断或读取失败”，保留底层原因；禁止将读取失败直接标记 `no_text_layer`。不能单凭最多六页的阴性结果断言整份无文字。
2. 对本批 RC4 样本建立最小逐页复现，检查依赖的加载、解密、解压与提取行为；评估修复原解析路径、升级依赖或采用本地备用提取器。不得预先认定引入 `pdftotext` 为最终依赖。需要口令的文件应明确报受保护，不索取或记录用户秘密，不写破解逻辑。
3. 为所有后端定义“正文可用 / 仅附件 / 有损或不完整 / 失败”的消费边界；告警与恢复动作应可被后续读取者取得。真实扫描件可以保留原件引用，但必须明确未识别正文；不凭空增加 OCR 能力声明。
4. 外部回退必须保持显式配置与数据发送边界，不因本次修复自动上传用户文档。HTML/文本质量验证与图片识别能力是否扩展分别确认，不捆绑扩大修复范围。
5. 设计已生成占位 raw 的安全重转入口：即使源哈希未变也可重试受影响解析结果；保护 pin、原文件和用户改动，重建受影响待办/引用的行为需验证。不得用“新文件解析正确”替代存量恢复验收。
