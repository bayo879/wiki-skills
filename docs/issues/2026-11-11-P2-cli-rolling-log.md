# CLI 滚动运行日志

优先级：P2

## 问题

用户要求在 `.wiki/` 内增加滚动 log，把 CLI 处理过程的信息写入，供后续排查问题。

现状证据（2026-11-11 源码）：

- `src/main.rs:34-45` 解析参数后直接 `dispatch`，没有统一的运行生命周期；每个 `run_*` 各自决定何时开始、何时 `report::emit`/`fail`。
- `src/report.rs:112,146` 在输出后直接 `std::process::exit`，结束点分散在信封里，没有集中的收尾入口。
- `src/layout.rs:19-44` 目前只有六个目录（`.wiki`、`cache`、`pages`、`pages/audit`、`raw`、`sessions`），没有日志目录；`open_repo` 经 `precondition::provision` 按 `LAYOUT` 补建，新目录必须进同一张表。
- 没有运行日志模块。旧 `.wiki/journal.jsonl` 按 [AGENTS 2.14](../../AGENTS.md) 只是只读历史，不能恢复写入，也不能作为新日志的格式依据。

## 影响

只靠最终输出无法还原失败前哪些步骤已经生效，尤其是部分成功、来源漂移、根收尾失败、索引刷新失败与并发锁竞争。日志实现不当还会反噬主流程：污染 stdout 的 JSON、与仓库锁或数据库写互相阻塞、并发追加导致事件交错、磁盘满或权限错误把本来成功的命令变成失败。

## 已确认

- 日志写失败时告警但继续业务，不因日志不可写阻断摄入（用户 2026-11-11 接受）。代价是这种情况下排查记录可能不完整。
- 运行日志不是决策日志、不是工具内历史、不是恢复机制；不改变「页面是唯一内容副本」与「没有工具内回退」的既有边界，旧 `journal.jsonl` 保持只读。
- 不记录源文件正文、页面完整载荷、查询返回内容；日志不进入页面树，也不进入 `query` 索引。
- 日志目录必须作为派生目录登记在 `src/layout.rs::LAYOUT`，由既有初始化/补建/`doctor --fix` 路径创建，不自造第二份目录清单。

## 候选方案

未定案：

- 独立的结构化事件日志，一行一事件（JSON Lines），每行同时带简短可读说明，而不是复制 stdout/stderr。同一次命令以运行标识关联，字段至少覆盖时间、运行标识、进程、命令、事件、级别、说明；任务/来源/目标标识与阶段耗时按需附加。
- 建议默认值（尚未确认）：单文件 10 MiB，保留最近 5 份（含当前文件），按大小轮转；单事件有长度上限。位置建议 `.wiki/logs/cli.log`，轮转文件与当前文件同目录。
- 记录点：命令开始与结束（含退出码、耗时）、阶段开始与结果、跳过原因、转换/合并/结算结果、警告与错误。panic 与「无法定位仓库」的早期错误能否写入、写到何处待定；硬终止可能没有结束事件，文档必须如实说明。
- 并发：单次追加使用 `O_APPEND`，轮转竞态只允许退化为「本轮不轮转」，不能丢事件、不能改变业务锁语义；具体轮转序列（rename 顺序、失败回退）未定。
- 告警通道：写失败时向 stderr 输出一次告警（不污染 stdout JSON），由进程内标记避免刷屏；是否同时进入命令的 warnings 未定。

## 待确认与验收条件

- [ ] 确认日志格式、默认大小/份数、单事件上限、告警通道与 panic 处理方式。
- [ ] 可按运行标识还原一次命令的流程，区分开始、成功、跳过、部分生效与失败；日志只是排查证据，不代替业务事实源。
- [ ] 多进程追加与轮转不产生交错、丢行或半行；不新增、不改变既有业务锁语义。
- [ ] 正文、载荷、查询结果与敏感参数不被整份复制；错误内容同样有泄露边界。
- [ ] 日志不可写、磁盘满、轮转失败都不使业务失败，也不破坏既有 JSON 信封与退出码。
- [ ] 日志目录登记在 `LAYOUT`，初始化、补建与修复符合既有边界；日志不进页面树与搜索索引。
- [ ] 测试覆盖成功、失败、部分生效、轮转、并发追加、日志不可写与磁盘满；现有输出快照不因日志改变。
- [ ] 实施后同步 `README.md`、`docs/readme/architecture.md` 与技能入口；技能只写「日志在哪、什么时候看」，不复制字段表。
