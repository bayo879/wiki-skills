# 设计原则

## 交付物是技能，不是程序

`skills/llm-wiki/` 整个目录就是交付物：`SKILL.md` 给 agent 读，`scripts/` 是引擎，
`references/curation.md` 是页面质量标准，`workflows/` 是随技能分发的内置工作流，
`templates/` 按类型放各页面的正文模板。
命令契约、安装、恢复与验证记录在
`docs/readme/` 与 `docs/agent/`，不放进技能目录。复制目录即可使用，没有服务、没有全局状态。

这是 2026-11-13 转型后的唯一形态。Rust CLI、单二进制分发、`output/` 发布包都已停止维护，
源码归档在 tag `rust-archive-2026-11-13`。

## 引擎与 agent 分工

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 引擎 | 扫描、解析、哈希、任务状态、载荷校验、引文核对、修订与渲染、观看区推送 | 判断哪份材料值得建页、写正文、选标题与边界 |
| agent | 读 raw 与已有页、决定来源归属、写正文与证据、提交载荷 | 直接改页面文件、手改数据库、跳过任务直接落盘 |

分工的边界由命令面固定：agent 日常只用 `ingest/next/submit/query/workflow`；
`check/doctor` 是诊断入口，`init/release/page/export/status/sync` 是人工或维护入口，不写进
技能流程。`sync` 只把观看区的手工修改回收进账本，不负责推送。**账本不是前置条件**：打开
账本的命令会补齐缺的目录、配置与表，补了什么列在 `repaired`，agent 不需要先自检再干活；
真出问题时错误里带恢复手册的 `doc` 与 `section`。没有"直接写页"的入口。

## 账本是唯一事实源

页面正文、修订、证据、来源摘要、任务状态都在 `.wiki/wiki.db`。引擎按账本把页面推送到
`<view>/pages/*.md`（`publish.dir`，默认 `wiki/`），那是给人浏览的观看区，不是输入。
`.wiki/` 里只有账本、原文、载荷与草稿，不再保存页面正文的第二份副本。

理由：如果页面文件是源，agent 顺手一改就会绕过引文校验与任务状态，且无法区分"人改的"与
"agent 改的"。把账本设为源后，页面必须经带校验的载荷写入。

观看区是免费的导出：离线浏览、diff、迁移都不需要额外命令。`export` 只是按
`type/id.md` 再渲染一份到指定目录，不读观看区。

观看区多了手工修改的回流通道：`<view>/pages` 被手改时推送只告警、不覆盖，由人工 `sync`
收进账本；只同步正文用 `sync --body-only`，元数据也改过的改用 `page import`。`<view>/raw`
由摄入维护：手改会在下一次 `ingest` 按整份正文被采纳为账本事实，共享它的来源一起换摘要、
文件不改名；`<view>/README.md` 每次推送重写。
`topics/`、`workflows/` 首次投放后归用户。

## 工作流是可执行能力，不是页面

知识页回答"是什么"，工作流回答"怎么做"，而且是 agent（或人）能照着执行的做法。工作流放在
`<root>/workflows/<id>/`，由 `WORKFLOW.md`、`scripts/`、`references/` 组成，只在显式
`workflow search` 后由 `workflow load` 返回主流程、分好类型的步骤和资源清单。项目工作流只从
`<root>/workflows/` 读取。

工作流不摄入、不进账本，理由有三点：

- 摄入管线是为"材料 → 知识页"设计的，要求引文与来源；工作流是操作指令，没有可核对的事实
  引文，混进 sources 只会让任务和页面索引变脏。
- 工作流需要边用边改。走摄入就要每次重新建任务、重新提交，改一个步骤的成本远高于收益；
  直接读文件可以让修改立即生效。
- 工作流不是事实源。流程步骤可以规定怎么做，但涉及"是什么"的判断仍要回到页面与 raw；
  这样账本仍是唯一事实源，工作流不会变成第二个知识库。

"可执行"由步骤类型固定下来：`## 步骤` 的每一步标 `tool:`、`human:`、`agent:` 或 `verify:`，
`workflow load` 直接返回 `tools`、`human_steps`、`agent_steps`、`verify_steps`，调用方不用
再解析正文。整份至少要有一步 `tool:`：只有人判断、没有可调用工具的流程是纯人工流程，应写成
`process` 页，`workflow load` 会判它不合法并指向 `process`。旧文件在 0.5.0 仍可加载但带
warning，0.6.0 起没有类型判无效。

只读也意味着 `workflow list` / `workflow search` / `workflow load` 不创建 `.wiki/`、
不依赖 `init`，在没有知识库的项目里也能单独使用。工作流检索与知识查询分开：`query` 只管
页面与话题，工作流必须显式检索，避免流程分支自动介入普通问答；代价是多一条命令，换来的
是主流程不被工作流带偏。

技能自带 `topic-exploration` 内置工作流，回答知识问题时默认进入：定主题、多轮检索、总结，
再问是否沉淀。默认进入靠的是显式 `workflow load "topic-exploration"`，不是 `query` 自动注入。
内置流程放在技能目录里，不依赖项目文件；项目需要定制时放同名工作流覆盖，显式检索的
`source` 会从 `builtin` 变为 `project`。

## 话题是 wiki 的探索层

话题属于 wiki 内容，放在 `<root>/topics/<主题>.md`，与 `workflows/` 同级，记录一次探索的主题、结论、
依据、未决问题、下一步和能力候选。它不是正式知识页：页面回答“是什么”且必须能回到 raw
引文；话题记录“查到了什么、还缺什么”，允许保留未验证的线索和下一步计划。

话题不摄入、不进账本，理由和工作流相同：它不是事实源，而是工作记录。把它放进摄入管线会
要求逐字引文，反而丢掉最有价值的“未决问题”和“下一步”。`query` 直接扫描话题，命中后
放在 `topics`，让下一次探索先读旧结论，再决定是否重新查证。

## 任务状态机约束流程

来源被摄入后不是"agent 自己决定从哪开始"，而是引擎给出 route/page 任务：

- 一份正文（一个 raw）一条 route 任务，同一份正文的多个路径合在一条里；route 通过后，每个目标页一条 page 任务。
- 任务有 `queued → leased → accepted`，另有终态 `expired`：来源或 raw 副本变化时任务被
  关闭，行保留供审计；领取带 15 分钟租约与递增 epoch。
- 提交按任务 id 关闭，不需要 epoch；租约过期或已关闭的任务返回 `E_TASK_STALE`，因来源或
  raw 漂移而 `expired` 的任务返回 `E_SOURCE_DRIFT`，都不会写入。
- agent 看到的是 brief/template，租约与 epoch 只在引擎内部使用。
- 校验失败零写入，任务退回队列并记录 `last_error`，修正后重新 `next`。

这样 agent 即使想跳过校验也没有接口；流程本身不是靠提示词约束，而是靠状态与校验。

## 不接管环境

技能不 OCR、不下载模型或语言包、不访问网络、不安装依赖。无文本层的文件标
`unsupported` 并给出提示，由人提供可复制文本。这条来自 2026-11-13 的一次事故：旧版技能
文档自相矛盾，agent 为补 OCR 自行下载语言包，被用户中止。

## 单机、单写者

SQLite 事务与文件原子替换保证单进程一致。多 agent 的场景约定"一个写者 + 其他只读"：租约
记着领取它的会话（`owner`，缺省取宿主注入的会话 id），别的会话来领取或摄入报
`E_INGEST_BUSY`、提交报 `E_TASK_FOREIGN`，不让多个会话轮流取同一队列；这仍不解决库级
并发写。批处理默认 20 条，够用且便于中断续跑。

## 出参自解释

每条命令的 `--json` 输出带 `ok`、`cmd`、`version`、`root`、`summary`、`data`（或
`error{code,message,next}`）。错误码稳定，`next` 写下一步动作。agent 不需要读源码就能
判断如何继续。
