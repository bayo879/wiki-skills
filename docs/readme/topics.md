# 话题沉淀

话题是一次探索的沉淀物：把「查过什么、结论是什么、还缺什么、下一步做什么」留成一份可
复用的 Markdown，下次遇到同一主题时接着做，而不是从头再查一遍。话题是 wiki 的探索层，
不是正式知识页，也不是聊天记录；它不进入账本，不参与页面引文校验。

## 位置与命名

```text
<view>/topics/
├── 复机办理.md
└── 反诈停机规则.md
```

- 一个主题一份文件，放在观看区 `<view>/topics/` 下（`publish.dir`，默认 `wiki/`）；它和
  `<view>/workflows/` 同级，属于知识库内容。
- 旧根目录 `<root>/topics/` 只作为兼容兜底保留一个发布版本：观看区优先，旧根只读；同名时
  观看区版本生效。
- 文件名用能检索的主题词，不用日期、`会话记录` 这类标题；同一个主题只维护一份。
- 目录不存在时不影响 `query`、`ingest` 等命令；打开账本的命令会创建 `<view>/topics/`，
  agent 也可以直接创建。

## 文件格式

frontmatter 建议写，缺了也能被检索：

```markdown
---
name: 复机办理
description: 停机复机的办理路径与时长
status: open
updated: 2026-11-16
---
```

`status` 取 `open`（还有未决问题）或 `done`（已收敛）。

正文固定六节，没有内容就写“无”：

```markdown
## 主题

要回答的问题、范围、不覆盖什么。

## 结论

先给结论，一段话能说清就不拆成条。

## 依据

- 页面：`anti-fraud-restore` — 复机路径与时长
- 原文：`raw:docs/a.md` — 关键数字或日期的出处
- 话题：`复机办理` — 上一轮的结论与未决问题
- 工作流：`topic-exploration` — 流程依据（不是事实依据）

## 未决问题

还需要确认什么，卡在哪里。

## 下一步

可执行的下一步：建议关键词、待摄入文件、待补页面。

## 能力候选

是否值得沉淀成工作流；值得就写工作流 id、触发条件、还缺哪几步。
```

「依据」节里、写成顶格 `- ` 列表项的这四类前缀会被引擎解析成结构化引用，其他节与缩进续行
不解析。目标要用反引号包起来：冒号后没有反引号 token（`页面：见下文`）、或前缀后直接跟反引号
（``页面::`x`` 的形态，即 `页面` 后不加空格）会在 `query` 时告警；前缀后先空格再接反引号
（``页面 `x``）会被当成叙述行忽略，不告警。指向不存在的页 / 原文 / 话题 / 工作流会列进
`missing`。每个话题最多保留 20 条引用，坏链也占名额，超出部分截断。

写作要求：

- 写结论、理由、适用条件、未确认事项；不抄整段原文。
- 区分实测事实、用户约束与推断；候选方案标为未验证。
- 内容脱离聊天也能读懂；三个月后能据此接着做。
- 不写密码、Token、API Key、个人联系方式。

## 与知识页、工作流、issue 的分工

| 内容 | 归属 |
| --- | --- |
| 项目事实（目录、命令、配置、已实现行为） | 项目产品文档 |
| 必须持续生效的规则 | 对应层级的指导文档，规则变更需用户授权 |
| 未决问题、待实现、待验收 | 项目 issues |
| 可复用的方法、经验、踩坑、方案取舍、探索结论 | `<view>/topics/` |
| 稳定、可重复执行、能落到工具上的流程 | `<view>/workflows/<id>/WORKFLOW.md` |

能力候选是话题的一节，不是工作流本身：流程稳定后先给工作流草稿，用户确认后再建，不直接改
工作流目录。

## 检索与摄入

- `ingest` 整目录跳过观看区与旧根 `topics/`，话题不会被当成来源，也不会生成 route/page 任务。
- `query` 先扫描 `<view>/topics/*.md`，再看旧根 `topics/`；命中时放在 `topics`，话题计数
  `topic_matches` 与页面 `matches` 分开。每项带 `name`、`description`、`status`、`path`、
  `origin`（`view` 或 `legacy`），按 `path` 直接打开话题文件。
  工作流候选在 `workflows`，最多 5 个、带 `applies`，但不会自动加载；需要按流程办事时核对后
  再 `workflow load`，也可显式 `workflow search`。
- 命中话题时每项带 `refs`（`pages` / `raws` / `topics` / `workflows` / `missing`，前四组是字符串
  数组，`missing` 是 `{kind, target}`）；普通文本 `query`（不含 `query --task`）命中页面时每项
  带 `citing_topics`，是引用过该页的话题名。`query --page` 同样给 `citing_topics`，有引用时文本
  里在 `incoming:` 之后多一行 `citing topics:`。
- 话题由 agent 直接写，不经账本、不排任务；写入后要报告“未执行摄入”，不能说成已建页。
- 话题改动立即对下一次 `query` 生效，不需要重新 `ingest`。

## 写入流程

1. 话题探索收尾，总结完成、结论能回溯到页面 id（源文件用 `query --page` 的 `sources[].raw` 定位）。
2. 默认问用户是否沉淀，并说明位置与要点；用户明确不留时不写。
3. 归属判断后写 `<view>/topics/<主题>.md`：已有同名话题就并入，不新建重复文件。
4. 收尾报告路径、`status`，以及两项后续：能力候选草稿、待查资料清单（来源、页面、
   建议关键词）。

## 边界

- 话题不是事实源：结论要能回到页面或 raw，冲突时以 raw 为准。
- 话题不替代产品文档、指导文档或 issues；不同归属的内容不塞进同一份话题。
- 凭据不落盘；范围含糊或含敏感内容时先澄清，必要时脱敏。
- 不跨工作区写入；`topics/` 始终在当前工作区的观看区下。
