## 1. [x] 统一文件变化检测的哈希口径

### 解决记录（2026-11-10）

统一全文摘要，扫描以大小与高精度修改时间初筛；固定的受限字节用于哈希和解析。复用 `parse.max_source_bytes`（默认 100MB），强制检查不能越上限，保留稳定窗口。元数据保持的变更仍可能漏检，需 `--force` 复核，不声称缓存绝对可靠。

证据：`tests/sync.rs::settled_large_source_uses_the_same_full_digest_for_scan_and_conversion`、`tests/sync.rs::same_second_equal_length_edit_is_not_hidden_by_metadata_cache`；`tests/convert_text.rs::direct_conversion_refuses_source_over_the_size_limit`；`tests/cli_ingest.rs::preview_force_large_does_not_bypass_the_byte_limit`。CLI 体积回归已执行通过；核心验证由主执行者收口。读取期间变化检测存在，不将其等同于已覆盖所有文件系统竞态。

### 问题与影响

扫描大文件使用抽样哈希，稳定性复核使用全文哈希。文件足够大、抽样没有覆盖全文时，两者可能不同，导致未变化的文件被误判为“本轮变化”，反复推迟转换。

依据：
- [扫描按体积分选全文/抽样哈希](../../src/scan.rs#L422-L429)。
- [防抖复核固定计算全文哈希](../../src/sync.rs#L401-L411)。
- [抽样读取头、中、尾窗口](../../src/hash.rs#L104-L144)。

### 已讨论方案：元数据初筛 + 全文哈希确认 + 体积上限

用户提出这一简化方向，尚未指定最大文件体积或授权实现。

1. 先检查文件大小，超过上限明确跳过并报告，不进入全文读取、解析。
2. `mtime + size` 用于快速筛选，不称为哈希；首次遇到或元数据变化时计算全文哈希。
3. 全文哈希相同则不重新转换，仅更新元数据记录；不同才转换。全链路不再混用抽样与全文哈希。
4. 在体积上限内，对同一份固定字节计算哈希并解析，避免哈希后重新打开源文件解析时读到另一份内容。读取过程中仍需检查增长/变化，不能只在读取前检查大小。
5. 保留文件稳定窗口：内容发生变化和文件已经写完不是同一个判断。
6. 保留强制全文检查入口：如果内容变化但 `mtime + size` 都被保留，快速筛选会漏检。具体入口及与现有 `--force` 的关系待确定。

### 待确认与验收

- [ ] 确认最大源文件体积；优先核对现有 `parse.max_source_bytes`，避免新建重复配置。
- [ ] 确认可接受元数据相同导致漏检的取舍，以及强制检查语义。
- [ ] 验证大文件稳定后可摄入，不再误报变化。
- [ ] 验证元数据变但内容不变时不重复转换；首次文件正常处理。
- [ ] 验证超限文件与读取过程中增长的文件受限，且源文件不被改写。
- [ ] 验证文件未稳定、读取期间被修改时不会交付不匹配的解析产物。

## 2. [x] 停止给每个候选自动追加本轮全部来源

### 解决记录（2026-11-10）

CLI 已取消候选发布。作者直接写正式页并显式填写实际使用的来源与更新日期，确认来源不修改页面；无需再定义“本轮候选”。旧库遗留不自动发布或删除。

证据：`tests/cli_done.rs::done_clears_only_one_source_and_repeating_it_is_a_noop` 验证页面字节不变且只清对应来源；`tests/cli_submit.rs::submit_is_rejected_without_touching_legacy_candidates` 验证旧入口拒绝且遗留字节保留。这些 CLI 测试已通过。来源真实性仍依赖作者判断，不承诺机器理解证据。

### 问题与影响

`submit` 默认遍历全部暂存候选，对每页追加全部 pending 来源。本轮 A、B 与某页的真实证据关系没有区分；遗留候选也会被处理。会产生无关引用，干扰关联页判断、来源重叠拦截和证据追溯。

依据：[选择全部候选及追加全部来源](../../src/ingest.rs#L379-L414)。

### 待评估方案（尚未定案）

由页面作者显式填写实际使用的 `sources`，工具校验引用合法性，不把“本轮摄入列表”当作“每页证据列表”。同时明确本轮候选与遗留候选的边界，避免不相关候选被统一刷新或发布。

### 待确认与验收

- [ ] 确认空来源页面如何处理，以及本轮候选范围如何表达。
- [ ] 本轮 A、B，页面仅使用 A，提交后不得自动多出 B。
- [ ] 遗留候选不得因新一轮摄入而被补入无关来源。
- [ ] 调整依赖自动追加行为的测试，复核重叠拦截与受影响页面查询。

## 3. [x] 将漂移检查基线绑定到 agent 实际读取的 raw 版本

### 解决记录（2026-11-10）

`ingest` 交付 raw 全文哈希；作者实际读 raw 时保存该值，`done` 必须携带所读版本，持锁核对 raw 和当前源后才清来源待办。旧哈希或源变化返回漂移并保留待办；重复确认成功无动作。

证据：`tests/cli_done.rs::done_with_an_old_raw_hash_keeps_the_new_work`、`tests/cli_done.rs::done_drift_is_exit_one_and_keeps_pending` 已通过。页面在确认前已生效，漂移不回滚页面，也不能证明作者确实读过资料或正文正确；这不是旧候选发布闸门的延续。

### 问题与影响

`current_hash` 在 `submit` 时读取当前 raw 才记录。agent 读取旧 raw 后，若下一轮转换更新 raw，再提交旧结论，基线可能已是新 raw；发布检查不能识别这种错配。

依据：
- [submit 时记录 raw 摘要](../../src/ingest.rs#L433-L450)。
- [发布时比较 manifest 与当前 raw](../../src/version.rs#L1256-L1272)。
- [begin 中 pending 的来源解析](../../src/ingest.rs#L246-L254) 与 [resolve_source](../../src/ingest.rs#L475-L494)：源摘要和 raw 摘要需区分，不能直接互换。

### 待评估方案（尚未定案）

在开轮交付时记录对应 raw 的全文哈希，之后不可在提交时用“当前值”覆盖该基线；提交/发布均对照这份基线检查。若允许新一轮摄入与旧候选并存，需要让候选能关联它实际读取的版本；仅给全局字段赋值更早，不一定足够。

### 待确认与验收

- [ ] 明确未完成轮次遇到新资料时，是禁止重开、合并，还是保留独立候选基线。
- [ ] agent 读旧 raw → raw 更新 → 提交旧候选，必须能识别错配，不能静默发布。
- [ ] 重试不得抹掉原始基线；源哈希与 raw 哈希各司其职。

## 5. [x] 修正开轮失败的成功退出与潜在漏单

### 解决记录（2026-11-10）

主摄入路径不再调用旧 begin/checkpoint。转换基线与来源待办在同一账本事务登记，入队错误向上返回；不能因转换已登记而悄悄丢掉交付任务。

证据：`tests/worklist.rs::failed_enqueue_rolls_back_conversion_baseline_and_can_retry` 用 SQLite BEFORE INSERT trigger 注入 ABORT，核对旧 sources/work_items 完整保留，解除故障后重试成功；主执行者报告该测试 GREEN。`tests/worklist.rs::successful_conversion_persists_a_recoverable_source_work_item` 覆盖重新打开库后待办仍在。该证据不覆盖断电、文件系统崩溃或任意写盘失败；raw 先写文件再记账的中断窗口仍由对账暴露，不宣称跨文件/数据库原子性。

### 问题与影响

转换成功后，`begin` 失败仅写 warning，不增加 `failures`；CLI 按 `failures` 决定退出码，因此可能成功退出。若 pending 未写成，已转换来源下一轮可能不再属于新增/变更，也没有待办接住。

“错误可能仍返回成功”可从分支直接看出；“哪些失败点会造成漏单及如何恢复”仍需故障注入确认，不能视为已复现。

依据：
- [待办合并与 begin 错误处理](../../src/sync.rs#L284-L307)。
- [CLI 根据 failures 选择退出码](../../src/main.rs#L357-L367)。
- [pending 写入与 checkpoint 顺序](../../src/ingest.rs#L324-L347)。

### 待评估方案（尚未定案）

开轮失败明确反映在结果和退出状态中，并确保转换完成但未成功交付的来源可重试。先定位各失败点的状态，再选择最小恢复机制；不能仅把 warning 改成错误就宣称不会漏单。

### 待确认与验收

- [ ] 对 pending 写入失败、checkpoint 失败分别注入故障。
- [ ] 失败必须有清晰非成功状态，并保留可恢复的工作记录。
- [ ] 故障排除后再次摄入可交付此前转换的来源，不要求用户改源文件制造变化。
- [ ] 验证重试不重复开轮或丢失遗留待办。
